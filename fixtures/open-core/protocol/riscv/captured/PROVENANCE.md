# Captured fixtures — RISC-V instruction trace

This directory holds traces acquired or produced from public open-source
projects. They complement the deterministic synthetic fixtures next door in
`../generated/` by exercising the decoder against real-world bus traffic.

## License allow-list

Captured fixtures must come from projects under one of these licenses:

- MIT
- BSD-2-Clause / BSD-3-Clause
- Apache-2.0
- ISC
- CC0-1.0
- public domain

GPL/AGPL/proprietary captures are excluded by policy. The static test
`test/static/captured_fixture_licenses_test.dart` walks every
`PROVENANCE.md` in the corpus and fails the build if any entry uses a
license outside this list, or if any fixture file in this directory has no
matching entry.

## Per-fixture entries

Each fixture committed below carries a block in this file with: source
project, source commit SHA, license + SPDX, author/maintainer, original
location of the testbench inside the source repo, capture method (direct
file from repo, or the exact `iverilog` / `verilator` / `cocotb`
invocation used locally), acquisition date, file size, scenario summary,
and 2–3 hand-verified anchor transactions confirmed by eye before the
snapshot was committed.

```markdown

```

## Current captures

## `riscv_ibex_rvfi_trap.fst` — real-core RVFI retire stream from lowRISC's Ibex, arithmetic → load/store → branch → trap

- **Source project:** lowRISC / Ibex — <https://github.com/lowRISC/ibex>
- **Source commit:** `3250d99482f1963891ef1cf19356eeaeeaa71d30` (acquired 2026-08-02)
- **License:** Apache License 2.0 (SPDX: `Apache-2.0`)
- **Author / maintainer:** lowRISC CIC (Ibex contributors; core derived from ETH Zurich / University of Bologna's zero-riscy)
- **Original location:** `rtl/ibex_top.sv` and its dependency closure, plus `vendor/lowrisc_ip/ip/prim_generic/rtl/` for the technology-generic prim cells. Ibex is **not** vendored into this repo — `helpers/ibex/Makefile` fetches the pinned commit. The tie-offs in our testbench are copied from upstream's own `examples/simple_system/rtl/ibex_simple_system.sv`.
- **Capture method:** built locally with `verilator --binary --timing --trace-fst +define+RVFI` against `ibex_top` in the upstream `small` configuration (`RV32M=RV32MFast`, `RV32B=RV32BNone`, `RV32ZC=RV32Zca`, `RegFile=RegFileFF`, `ICache=0`, `SecureIbex=0`, `PMPEnable=0`, `WritebackStage=0`, `BranchTargetALU=0`, `MHPMCounterNum=0`), Verilator 5.050 (2026-07-01). Verilator ignores the scope/level arguments to `$dumpvars` and `--trace-depth` cannot separate `ibex_top` from its inlined children, so the raw dump carries the whole hierarchy (2596 signals, 42530 bytes) and is trimmed afterwards by `helpers/ibex/trim.py` via `fst2vcd` → filter → `vcd2fst`. Full recipe + pinned fetch under `helpers/ibex/`.
- **Acquired:** 2026-08-02
- **Size:** 42530 bytes raw / 1841 bytes committed (trimmed to clock, reset and the 21 RVFI channels WaveCrux binds).
- **What it exercises:** The first capture in this corpus from RTL nobody on this project wrote. A hand-assembled RV32I program (no RISC-V toolchain — `helpers/ibex/assemble.py` encodes the words directly) runs 26 instructions through Ibex's two-stage pipeline: register-immediate and register-register arithmetic, a word store/load pair, byte and halfword store/load pairs, a forward `beq`, a three-iteration countdown loop closed by a backward `bne`, and an `ecall` that traps into a handler at the reset `mtvec` vector. Its value is that the signal names, hierarchy depth, channel widths and retirement timing are whatever Ibex actually emits — the RVFI bundle sits at `tb_ibex_rvfi.u_ibex_top`, two scopes deep, alongside 17 non-channel `rvfi_ext_*` siblings that auto-detection must not bind.
- **Hand-verified anchors:**
  - PC=0x080, t=85 ns: `0x12300093` → `addi ra, zero, 291`. Ibex's reset vector is `boot_addr_i + 0x80`, and `boot_addr_i` is tied to 0, so this is the first instruction executed.
  - PC=0x094, t=145 ns: `0x0032A023` → `sw gp, 0(t0)` with `rvfi_mem_addr=0x200`, `rvfi_mem_wmask=0xF`, `rvfi_mem_wdata=0x579` — confirming `0x123 + 0x456` landed in `gp` two retirements earlier.
  - PC=0x0A8, t=225 ns: `0x00828223` → `sb s0, 4(t0)` with `rvfi_mem_wmask=0x1` at `0x204` — byte-granular mask, distinct from the word case above.
  - PC=0x0C8, t=415 ns: `0x00000073` → `ecall` with `rvfi_trap=1`; the next retirement is at PC=0x000 with `rvfi_intr=1`, i.e. the trap vector was entered.
- **Snapshot regenerated by:** `REGENERATE=1 flutter test test/services/decoders/riscv_captured_fixtures_test.dart`
- **Note on two RVFI deviations in upstream Ibex:** the consistency checker reports 21 violations against this trace, and they are **not** suppressed. (1) `rvfi_mem_rmask` is `4'b1111` on every non-store, because `ibex_core.sv:1653` derives it from `lsu_type` alone and the decoder's unconditional default for `data_type_o` is the word encoding (`ibex_decoder.sv:227`) — nothing gates it on whether a memory request was issued. (2) `rvfi_pc_wdata` is PC+4 rather than the handler address on a trapping instruction, because `ibex_core.sv:1652` samples it when the ID stage completes, one cycle before the controller applies the exception redirect. Neither field is checked by Ibex's own DV, and upstream's `doc/03_reference/rvfi.rst` states Ibex "is not yet formally verified". Full write-up in `test/services/riscv/riscv_ibex_captured_rvfi_test.dart` and `verification/VERIFICATION_GUIDE.md` §10B.
- **Note on decode coverage:** the two `csrrs` instructions and the `wfi` in the trap handler render as `UNKNOWN INSN` in the committed snapshot. That is correct for the current asset set — `assets/decoders/isa/riscv/` ships RV32I/M/A/F/C and RV64I/M/A/D/C, with no Zicsr or privileged-system TOML. The capture records the gap rather than working around it.
- **Note on X-propagation:** Verilator is a two-state simulator, so this capture has no `x`/`z` samples anywhere, including at time zero. A four-state capture (Icarus, VCS, Questa) would exercise `RiscvRetiredInstruction.hasUnknownBits`; this one deliberately does not, and the test asserts the absence so it cannot be mistaken for coverage.

## `riscv_picorv32_wb_ez.fst` — RV32I instruction-fetch trace of the upstream picorv32 `testbench_ez` loop

- **Source project:** YosysHQ / picorv32 — <https://github.com/YosysHQ/picorv32>
- **Source commit:** `87c89acc18994c8cf9a2311e871818e87d304568` (acquired 2026-05-31)
- **License:** ISC (SPDX: `ISC`)
- **Author / maintainer:** Claire Xenia Wolf
- **Original location:** `picorv32.v` (the RV32I core + its `picorv32_wb` Wishbone-master wrapper). The six-instruction loop body is the same one that ships in upstream `testbench_ez.v` (public domain).
- **Capture method:** built locally with `iverilog -g2012 -o tb_picorv32_riscv_ez.vvp tb_picorv32_riscv_ez.v picorv32.v && vvp tb_picorv32_riscv_ez.vvp -fst`. Helpers + reproducible build under `helpers/picorv32/`.
- **Acquired:** 2026-05-31
- **Size:** 5766 bytes raw / 5766 bytes committed (FST already compact at this scale).
- **What it exercises:** A pure-Verilog testbench drives YosysHQ's `picorv32_wb` (Wishbone master) against a 256-word in-memory WB slave preloaded with the upstream `testbench_ez` six-instruction loop body. `picorv32_wb`'s otherwise-tied-off `mem_instr` port is connected and a derived `ifetch_valid = wb_ack & mem_instr` strobe is bound as the RISC-V decoder's `valid` slot — so data load/store transactions on the shared bus are skipped and only completed instruction fetches contribute to the decoded stream. Seven ifetch completions covering one full loop iteration plus the wrap-around fetch.
- **Hand-verified anchors:**
  - PC=0x0000, t=80 ns: `0x3FC00093` → `addi ra, zero, 1020` (the `li ra, 1020` pseudo).
  - PC=0x0014, t=480 ns: `0xFF5FF06F` → `jal zero, …` (-12-byte backward branch).
  - PC=0x0008, t=590 ns: `0x0000A103` → `lw sp, 0(ra)` — the first ifetch of the second iteration, confirming the `jal` landed at `loop:` as expected.
- **Snapshot regenerated by:** `REGENERATE=1 flutter test test/services/decoders/riscv_captured_fixtures_test.dart`
- **Note on disassembler output:** the `jal`'s formatted immediate field shows `-2561` rather than the architectural `-12`. This is the documented JKU/Surfer TOML schema behavior — see `verification/VERIFICATION_GUIDE.md` §5.9.10. The PC chain is correct (next ifetch lands at PC=0x08); only the displayed immediate departs from architectural byte units, identically to Surfer.
